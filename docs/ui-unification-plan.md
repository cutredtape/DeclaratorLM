# План уніфікації дизайн-елементів — DeclaratorLM

Покроковий план приведення візуальної системи `declarator-lm/src/index.css` (~6200 рядків) до узгодженої шкали токенів. Доповнює [ui-consistency-audit.md](ui-consistency-audit.md), який фіксує **що** не так; цей документ описує **як** це виправити, не зламавши застосунок.

Головний принцип: **фази впорядковані за ризиком, а не за категорією.** Спершу йде все, що фізично не може змінити розкладку (кольори, радіуси), і лише потім те, що може (кегль, розміри іконок). Кожна фаза самодостатня — її можна зупинити чи відкотити, не блокуючи наступні.

## 1. Аналіз безпеки: що саме може зламатися

Перед плануванням я перевірив реальні залежності в коді. Нижче — п'ять справжніх ризиків із доказами, і чому запропонований план у них не впирається.

### Ризик 1 — перейменування CSS-класів ламає JS **без помилки збірки**
Частина класів використовується не лише для стилів, а й як селектори в JavaScript:

| Селектор | Де запитується |
|---|---|
| `[data-flip-key]` | `VisualLogPanel.jsx:102` (FLIP-анімація стрічки карток) |
| `dossier-lg-item--off` | `DossierCharts.jsx:111-112` (перемикання серій легенди) |
| `dossier-x-label--active` | `DossierCharts.jsx:128` |
| `dossier-dot`, `dossier-dot--analyzed` | `DossierCharts.jsx:163` |
| `[data-xi="…"]` | `DossierCharts.jsx:127` |

Перейменування будь-якого з них зламає поведінку **тихо** — Vite збереться успішно, помилка виявиться лише при кліку в UI.

> **Запобіжник:** цей план **не перейменовує жодного класу.** Змінюються тільки *значення* властивостей і додаються нові змінні. Це знімає ризик повністю, а не пом'якшує його.

### Ризик 2 — англійська версія перекладається за **точним збігом тексту**
`i18n/domTranslate.js` обходить DOM і підміняє текстові вузли та атрибути (`title`, `aria-label`, `placeholder`, `alt`), які точно збігаються з ключем у `enCatalog.js` (`domTranslate.js:62-72` — спершу точний збіг, потім нормалізований). Класи й стилі він не чіпає взагалі.

> **Наслідок:** чисто стильові зміни для i18n безпечні. Але **будь-яка зміна видимого тексту потребує запису в `enCatalog.js`**, інакше рядок залишиться українською в EN-збірці.
>
> *Перевірено заднім числом:* минула зміна «Закрити» → «Скасувати» в `CloudComparisonModal` безпечна — обидва рядки вже в каталозі (`enCatalog.js:193` і `:437`), кнопка коректно стала «Cancel».

### Ризик 3 — посилання на неоголошений токен **тихо вимикає властивість**
`border-radius: var(--radius-xl)` при невизначеному `--radius-xl` робить властивість недійсною — кут стає прямим, без жодного попередження. Це головна пастка саме токен-міграції.

> **Запобіжник:** механічна перевірка цілісності токенів після кожної фази (команда в §5). Зараз стан чистий — перевірка знаходить три «неоголошені» токени, і всі три легітимні: `--risk-color` задається інлайново з JSX (7 місць), `--fp-search-h` — з JS у рантаймі (`App.jsx:3473`), обидва з фолбеками. Третій, `--danger` (`index.css:2506`), — «висяча» посилка, яка ніколи не була оголошена й завжди падає на фолбек `#c53030`; це радше сміття, ніж баг (див. Фазу 0).

### Ризик 4 — зміна кегля та розмірів іконок **змінює розкладку**
Вікно застосунку фіксоване (1180×820, `webview_app.py`), а в картках активно вживається `white-space: nowrap` + `text-overflow: ellipsis`. Зменшення/збільшення кегля зсуває точку обрізання тексту й може переносити рядки.

Масштаб ризику я виміряв, а не припустив: серед правил, де напівпіксельний кегль поєднується з `ellipsis`, знайшлося лише **3 місця** (2× `11.5px`, 1× `9.5px`). Тобто ризик реальний, але локалізований.

> **Запобіжник:** типографіка йде окремою пізньою фазою, дрібними партіями, зі знімком обчислених стилів до/після (§5).

### Ризик 5 — палітра графіків продубльована через межу Python/JS
`dossier_charts_html.py:26-48` хардкодить ті самі hex-кольори серій, що й `dossierChartConfig.js`, але рендерить **світлу** тему з власним префіксом класів `dossier-html-*` і власним CSS (`index.css` туди не потрапляє взагалі).

> **Наслідок:** зміни фронтенд-CSS **не досягають** HTML-звіту — це ізоляція, а не поломка. Але якщо колись міняти саму палітру серій, обидві сторони треба правити разом, інакше живі графіки в застосунку й графіки у звіті розійдуться. Цей план палітру серій **не чіпає** (див. §6).

### Ризик 6 (операційний) — зміни не видно без перезбірки
`declarator-lm/dist/` у `.gitignore` (рядок 24). Правка `index.css` не впливає на застосунок, доки не виконано `npm run build`.

## 2. Залізні правила (інваріанти всіх фаз)

1. **Жодних перейменувань класів і жодних змін розмітки.** Тільки значення властивостей + нові оголошення токенів.
2. **Жодних змін видимого тексту.** Якщо все ж знадобиться — синхронний запис у `enCatalog.js`.
3. **Токен спершу оголошуємо, потім використовуємо** — у межах одного коміту, з перевіркою цілісності після.
4. **Одна фаза — один коміт.** Відкат будь-якої фази не має зачіпати попередні.
5. **`prefers-reduced-motion` не деградує.** Кожен новий/змінений анімований елемент лишається у відповідному виключенні (`index.css:4134+`).
6. **Тема deep-research лишається робочою.** `.app.app--deep-research` (`index.css:4224-4239`) перевизначає токени в рантаймі — усі нові токени мають бути сумісні з цим перевизначенням (тобто не хардкодити те, що має бути змінною).

### Фаза 1 — Шкала радіусів (нульовий ризик розкладки)

Радіус не впливає на розкладку взагалі — тільки на вигляд кутів. Це найбезпечніша фаза, тому вона перша серед уніфікаційних.

**Поточний стан:** 16 різних числових значень. База `6px` домінує (34 використання: 23 через `var(--radius)` + 11 літералом), решта — розсип.

**Цільова шкала** (підібрана так, щоб максимум сайтів лишився без змін):

```css
--radius-xs:   3px;    /* дрібні індикатори, смужки, свотчі */
--radius:      6px;    /* БАЗА — вже існує, не чіпаємо */
--radius-md:   8px;    /* вкладені блоки, дропдауни */
--radius-lg:  10px;    /* вже існує — плитки, спливні панелі */
--radius-xl:  12px;    /* картки, модалки */
--radius-pill: 999px;  /* пігулки, бейджі */
```

`50%` (9 використань) лишається літералом — це справжнє коло, семантично інша річ, а не крок шкали.

**Мапінг:**

| Було | Стало | К-сть сайтів | Дельта |
|---|---|---|---|
| `2px`, `4px` | `--radius-xs` (3px) | 6 | ±1px |
| `5px`, `7px` | `--radius` (6px) | 4 | ±1px |
| `8px` | `--radius-md` | 6 | 0 (лише токенізація) |
| `9px`, `11px` | `--radius-lg` (10px) | 3 | ±1px |
| `12px`, `13px`, `14px` | `--radius-xl` (12px) | 6 | 0…−2px |
| `99px` | `--radius-pill` (999px) | 10 | 0 (візуально ідентично) |

Разом ≈29 правок значень + 4 нові оголошення. Максимальна дельта — 2px на кутах карток досьє; решта — 1px або нуль.

> Побічно: `7px`, який я сам додав минулого разу для кнопок у картках помилок, згортається назад у базовий `var(--radius)` — це було моє власне відхилення від системи.

**Перевірка:** `npm run build`; перевірка цілісності токенів; знімок обчислених стилів (§5) — очікувані зміни лише у властивості `border-radius`, будь-яка зміна `width`/`height`/`font-*` = регресія.

### Фаза 2 — Кольори станів і фокус-кільця (нульовий ризик розкладки)

**2.1 Уніфікувати ширину фокус-кільця.** Зараз співіснують `0 0 0 2px` (активні стани: `.file-picker-search-toggle--open`, `.queue-btn--active`) і `0 0 0 3px` (фокус інпутів). Пропозиція: лишити **саме цей поділ**, але зафіксувати його токенами, бо він осмислений — «активний» і «у фокусі» це різні стани:

```css
--ring-active: 0 0 0 2px var(--accent-glow);
--ring-focus:  0 0 0 3px var(--accent-glow);
```

**2.2 Звести клавіатурний фокус до одного вигляду.** Три різні `:focus-visible` (2px суцільний акцент / 1px суцільний акцент / 1px **пунктирний сірий**) → один:

```css
outline: 2px solid var(--accent);
outline-offset: 2px;
```
Сайти: `index.css:280` (без змін), `:2939` (1px→2px), `:1974` (пунктирний сірий → суцільний акцент).

**2.3 Порожні/помилкові стани.** Звести три одноразові варіанти в `UsageDashboard.jsx` (`.usage-dash-sub`, `.usage-dash-empty-hint`, `.usage-dash-muted`) і `.dossier-charts-empty` до єдиного токена кольору `--text-muted` + спільного класу-контейнера за зразком `.log-empty` (`index.css:3436`), який уже є найкраще спроєктованим порожнім станом у застосунку.

> ⚠️ Тут єдина точка, де фаза торкається розмітки: `.dossier-charts-empty` довелося б замінити на `.log-empty`. Оскільки інваріант №1 забороняє чіпати класи, **робимо навпаки**: лишаємо класи на місці й вирівнюємо їхні *значення* під `.log-empty`. Нуль ризику, той самий візуальний результат.

**Перевірка:** збірка; знімок обчислених стилів; ручна перевірка фокуса з клавіатури (Tab) по модалці й сайдбару.

### Фаза 3 — Типографічна шкала (⚠️ змінює розкладку)

Найбільша за обсягом і єдина по-справжньому ризикована фаза. **Виконувати окремо від усіх інших**, партіями.

**Поточний стан:** 25 різних значень `font-size`, без жодного токена. Справжня проблема — напівпіксельні кеглі (43 використання), які майже завжди стоять поруч зі своїм цілим сусідом.

**Цільова шкала:**

```css
--fs-3xs:  9px;   --fs-2xs: 10px;   --fs-xs:  11px;   --fs-sm:  12px;
--fs-md:  13px;   --fs-lg:  14px;   --fs-xl:  16px;
```
Кеглі 18px і більше (18/19/22/24/27/28/30/32/46) лишаються літералами — це поодинокі «геройські» числа дашборду, токенізація їх нічого не дає.

**Мапінг і порядок партій** (від найбезпечнішої до найризикованішої):

| Партія | Було → Стало | Сайтів | Чому такий порядок |
|---|---|---|---|
| 3a | `12.5px` → `--fs-sm` (12px) | 6 | Найменша партія, дельта 0.5px |
| 3b | `13.5px` → `--fs-md` (13px) | 4 | Те саме |
| 3c | `9.5px` → `--fs-3xs` (9px) | 2 | Одне з них — у контексті `ellipsis`, перевірити окремо |
| 3d | `10.5px` → `--fs-xs` (11px) | 11 | Заразом лікує «трійцю eyebrow-лейблів» з аудиту |
| 3e | `11.5px` → `--fs-xs` (11px) | 20 | **Найбільша й найризикованіша**: 2 сайти в контексті `ellipsis` |
| 3f | `15px`, `17px` → `--fs-xl` (16px) | 7 | Заголовки, дельта 1px |
| 3g | Токенізація решти (11/12/13/14px) без зміни значень | ~100 | Механічно, нульова дельта |

**Окремо — розбіжність «назви картки»** (14px/600 у логу vs 16px/700 у досьє vs 13.5px/600 у дашборді). Тут потрібне *рішення*, а не механічна заміна: три компоненти показують той самий смисловий елемент. Рекомендація — `--fs-lg` (14px) + вага 600 як єдиний вигляд, але це видима зміна ієрархії в досьє-панелі, тож її варто затвердити окремо.

**Перевірка (обов'язкова для кожної партії):** знімок обчислених стилів + прицільна перевірка `scrollWidth > clientWidth` на елементах з `ellipsis` до/після (скрипт у §5) — це ловить зміну точки обрізання механічно, без ока.

### Фаза 4 — Розміри іконок (⚠️ рекомендую **звузити**, а не робити повністю)

Аудит зафіксував 22/26/28/30/34/38/42/52/64px для схожої ролі. Спокуса — звести все до 4-5 кроків. **Не рекомендую** робити це механічно: ці елементи стоять у різних flex-контекстах, і, наприклад, 22px→28px це +27% розміру в рядку поруч із текстом — видимий зсув розкладки заради «чистоти таблиці».

Це рівно та пастка, про яку йшлося в аудиті: механічне вирівнювання до «найближчого наявного значення» просто перемістить довільність, а не прибере її.

**Рекомендована звужена дія:** оголосити токени лише для розмірів, які **вже** мають стабільну роль і збігаються між компонентами —

```css
--icon-avatar: 52px;  /* кругла іконка-аватар картки (visual-log-card-icon, visual-log-loader) */
--icon-gauge:  64px;  /* великий гейдж досьє */
```
— і **не чіпати** 22/26/30/38, доки не буде візуального перегляду кожного випадку живою людиною.

## 5. Протокол перевірки

Три механічні перевірки, які не потребують скріншотів.

**(а) Цілісність токенів** — ловить головну пастку міграції (посилання на неоголошену змінну). Має повертати лише три відомі рантайм-змінні:

```bash
cd declarator-lm/src && comm -23 <(grep -oE 'var\(--[a-zA-Z0-9-]+' index.css | sed 's/var(//' | sort -u) <(grep -oE '^\s*--[a-zA-Z0-9-]+\s*:' index.css | tr -d ' :' | sort -u)
```

**(б) Збірка** — ловить синтаксичні помилки CSS/JSX:

```bash
cd declarator-lm && npm run build
```

**(в) Знімок обчислених стилів до/після** — ловить непередбачені зміни. Через dev-сервер (`npm run dev`, порт 1420) виконати в консолі сторінки, зберегти вивід до і після фази, порівняти:

```js
JSON.stringify([...document.querySelectorAll('[class]')].slice(0, 400).map(el => {
  const s = getComputedStyle(el);
  return [el.className, s.fontSize, s.borderRadius, s.width, s.height,
          el.scrollWidth > el.clientWidth];
}))
```
Останнє поле — прапорець «текст обрізається». Для Фаз 1–2 будь-яка зміна `width`/`height`/`fontSize` = регресія. Для Фази 3 зміни `fontSize` очікувані, а от новий `true` у прапорці обрізання — регресія.

> ⚠️ Обмеження: у поточній сесії панель браузера не показувала скріншоти, тож усі перевірки нижче побудовані на обчислених стилях і збірці. **Фінальний візуальний огляд живого застосунку (`python webview_app.py`) лишається за людиною** — механічні перевірки ловлять зсуви розкладки, але не «стало негарно».
